# Agentic SDLC Pipeline — Project Plan

## Project: Agentic SDLC Pipeline

A Claude Code-native agentic pipeline that accepts any Python project user story and drives it through the full SDLC — from requirements to a merged PR — entirely via Claude agents, skills, and hooks. You interact only with the orchestrator; it manages all specialist agents internally.

---

## Interaction Model

| Level | Steps | Behavior |
|---|---|---|
| L1 — Deep Interactive | Requirements, Architecture | Run in the orchestrator's main thread via skills (`requirement-analysis`, `architecture-design`) so it can ask you clarifying questions directly; iterates until you approve |
| L2 — Run + Approve | Design Review, Impl Planner, Implementation, Code Review, Verification, Doc Sync | Subagent runs autonomously, orchestrator shows output and asks: **approve / revise (with feedback) / abort** |
| L3 — Explicit Approve | PR | Orchestrator shows full PR draft; only creates PR after your explicit confirmation |

**Entry point**: `claude --agent orchestrator` (or `"agent": "orchestrator"` in `.claude/settings.json`), then: `process user-stories/user-story-1.md`  
The orchestrator must run as the main-thread agent — subagents cannot spawn other subagents, so it cannot be started with `@orchestrator`.  
**You never invoke subagents directly.**

**Feedback loops**: Design Review blockers return to Architecture; Code Review issues or failing Verification return to Implementation. Each loop is capped at 2 retries, then the orchestrator escalates to you.

## Pipeline Flow

```
user-stories/user-story-N.md
        │
        ▼
[ORCHESTRATOR] ──────────────────────────────────────────────┐
        │                                                     │
        ├─[L1]─► Requirements (skill) ──► docs/requirements.md│
        │                                                     │
        ├─[L1]─► Architecture (skill) ──► docs/architecture.md│
        │                                                     │
        ├─[L2]─► Design Review Agent ──► docs/design-review.md
        │                                                     │
        ├─[L2]─► Impl Planner Agent ──► docs/impl-plan.md    │
        │                                                     │
        ├─[L2]─► Implementation Agent ──► src/ + tests/      │
        │                                                     │
        ├─[L2]─► Code Review Agent ──► output/reports/       │
        │                                                     │
        ├─[L2]─► Verification Agent ──► output/test-results/ │
        │                                                     │
        ├─[L2]─► Doc Sync Agent ──► docs/ (updated)          │
        │                                                     │
        └─[L3]─► PR Agent ──► GitHub Pull Request            │
                                                              │
        All agents report back to orchestrator ──────────────┘
```

### Phase 3 — Specialist Agents
**Goal**: Create all 9 specialist agent files with clear system prompts and input/output contracts.

Agent input/output contracts:

| Agent | Input | Output |
|---|---|---|
| requirements | user story file | `docs/requirements.md` |
| architecture | `docs/requirements.md` | `docs/architecture.md` |
| design-review | `docs/architecture.md` | `docs/design-review.md` |

| pr | all docs + test results (embedded in PR body, since `output/` is gitignored) | GitHub Pull Request URL |

The requirements and architecture agent files define the L1 behavior; the orchestrator executes them in the main thread via the matching skills so it can interact with you.

### Phase 4 — Orchestrator Agent
**Goal**: Create the orchestrator — the single entry point that drives the full pipeline.

Orchestrator responsibilities:
- Read user story file passed as argument
- Run as the main-thread agent (`claude --agent orchestrator`); run L1 steps via skills, spawn L2/L3 specialists with the Agent tool
- Apply interaction level rules (L1/L2/L3) per step; L2 offers approve / revise / abort
- Route failures back through bounded feedback loops (max 2 retries) before escalating
- Resume interrupted runs by skipping steps whose output already exists (`--fresh` regenerates everything)
- Gate each step: check output file exists and is non-empty before proceeding
- Append run log to `docs/changelog.md` after each step
- Surface errors clearly if a gate fails

Tasks:
- [ ] `.claude/agents/orchestrator.md` — full controller logic with all 9 steps, gating, and interaction levels

**Deliverable**: Orchestrator agent file committed.

---

### Phase 5 — Hooks
**Goal**: Configure Claude Code hooks for logging and quality gates.

Hooks to configure in `.claude/settings.json`:
- [ ] `PreToolUse` (matcher `Agent`) → log `tool_input.subagent_type` to `docs/changelog.md`
- [ ] `PostToolUse` (matcher `Write`) → validate output files are non-empty after each agent writes
- [ ] `Stop` hook → print pipeline summary only when the PR step has completed (the hook fires after every turn, so guard it)

Hook commands receive their event as JSON on **stdin** (parse with `python -c` / `jq`); there is no `CLAUDE_TOOL_INPUT` env var.

**Deliverable**: `.claude/settings.json` with hooks configured and committed.

---

## Success Criteria

- [ ] Single invocation (`claude --agent orchestrator`, then `process user-stories/user-story-1.md`) drives the entire pipeline
- [ ] Requirements and Architecture steps ask clarifying questions interactively
- [ ] All other agents run autonomously and wait for human approval (approve / revise / abort) before proceeding
- [ ] Review/verification failures loop back to Implementation (max 2 retries) before escalating
- [ ] PR is only created after explicit user confirmation
- [ ] All `docs/*.md` artifacts are populated and human-readable
- [ ] Generated Python code passes tests
- [ ] No subagent is ever invoked directly by the user

---

## Notes

- All agents are `.claude/agents/*.md` files (Claude Code native)
- No external SDK or API keys required beyond what Claude Code already uses
- Pipeline is resumable: existing, non-empty outputs are skipped on re-run; use `--fresh` to regenerate all artifacts
- One user story per repo/branch at a time — `docs/` and `src/` are shared, so a second story needs a fresh clone or branch
- The pipeline is general-purpose: works for any Python project user story
